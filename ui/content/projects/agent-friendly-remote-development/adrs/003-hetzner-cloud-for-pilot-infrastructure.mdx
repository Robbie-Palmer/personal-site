# Context

The pilot already runs on a Hetzner CX33. That lowers migration risk without
settling the infrastructure-provider choice.

Infrastructure as code is a product requirement for this project. Coding
agents must be able to inspect a versioned definition, propose a change, create
or replace infrastructure, detect drift, and tear down a test environment. A
provider that needs routine console work leaves important state outside the
repository and makes both agent operation and disaster recovery less reliable.

This ADR compares providers of general-purpose virtual machines: Hetzner Cloud,
Hostinger, netcup, OVHcloud, and Oracle Cloud. It considers kube-hetzner as
evidence about the Hetzner automation ecosystem, not as another provider.

# Decision

Use Hetzner Cloud for the pilot and for the next host under the current
single-node architecture. Keep NixOS as the host definition and K3s manifests
as the workload definition.

Manage the provider layer through a pinned version of the official
`hetznercloud/hcloud` Terraform provider. The declared baseline must include
the server, SSH keys, primary IP, firewall, network, and any attached volume.
After an emergency console change, update the code to match or revert the
change.

Keep encrypted workspace backups independent of Hetzner. Provider snapshots
and backups may shorten recovery, but they do not replace a restore path that
works on a newly provisioned machine.

Do not adopt kube-hetzner for the existing single NixOS node. Reconsider it for
a greenfield multi-node Hetzner cluster where automated node replacement,
private cluster networking, load balancers, or autoscaling justify a
cluster-specific Terraform module.

# Selection criteria

Apply these criteria in order. A lower price does not compensate for failing
the first two.

1. **Declarative lifecycle:** an actively maintained provider can create,
   update, import, and destroy the VM and its required network, firewall, IP,
   SSH-key, and storage resources without routine console steps.
2. **Reproducible host:** the automation can install or bootstrap the declared
   NixOS system and produce an idempotent second plan.
3. **Operational fit:** the provider offers documented APIs, predictable
   deletion and billing, suitable European regions, and a credible recovery
   path.
4. **Continuity:** normal paid capacity is available and is not subject to an
   idle-use reclamation policy.
5. **Cost:** compare the full recurring cost only after the automation and
   continuity gates pass.

## Why the OVHcloud rejection still stands

The earlier shorthand that OVHcloud "does not support IaC well" was directionally
useful but too broad. OVHcloud has an official Terraform provider, and
`ovh_vps` first appeared in April 2024. The provider added SSH-key and image
installation fields in July 2025. Creating a VPS from Terraform now works.

The remaining concern is the completeness and reliability of the VPS lifecycle.
The open comprehensive-coverage work lists gaps around image discovery,
reinstallation, snapshots, automated backups, networking, power operations,
and existing creation fields. Recent provider fixes also addressed a VPS that
tainted itself after creation. Those gaps leave the VPS lifecycle behind
Hetzner's established, integrated resource set for this project.

OVHcloud's VPS-2 currently lists a lower monthly price than the Hetzner CX33
plus IPv4 and includes a daily backup. The difference is too small to accept a
weaker automation path. Reconsider OVHcloud when its comprehensive VPS coverage
has landed and the provider passes the acceptance test below without console
work.

## What kube-hetzner changes

[kube-hetzner](https://github.com/kube-hetzner/terraform-hcloud-kube-hetzner)
is a well-developed Terraform module for K3s or RKE2 on Hetzner Cloud. It
supports single-node and highly available clusters, private networking,
Hetzner's cloud controller and storage driver, multiple CNIs, automated
updates, load balancers, and autoscaling.

That ecosystem strengthens the Hetzner choice because the project has a
declarative growth path. It does not justify replacing the current NixOS host.
The module owns the machine image and cluster topology, while the present
deployment already declares those concerns in NixOS and direct K3s
configuration.

# Provider acceptance test

A future provider candidate must pass this test in a disposable project before
it can replace Hetzner:

1. Create the network, firewall, SSH key, IP, server, and volume from versioned
   Terraform or OpenTofu configuration.
2. Bootstrap the declared NixOS host without a provider-console step.
3. Run a second plan with no unexplained changes.
4. Restore an encrypted workspace backup and run the standard build and private
   access checks.
5. Replace the server while preserving the documented durable state.
6. Destroy every test resource from code and reconcile the final invoice.

# Consequences

### Benefits

* Agents and humans work from the same reviewable infrastructure definition.
* The provider decision rests on lifecycle automation rather than the smallest
  advertised monthly price.
* The current host avoids migration risk and has a credible declarative path to
  a larger Hetzner cluster.
* The acceptance test makes a later provider comparison reproducible.

### Costs

* Hetzner may cost slightly more than a comparable OVHcloud VPS and charges
  separately for backups.
* Provider-specific Terraform remains necessary at the lowest infrastructure
  layer.
* Direct NixOS and K3s operation remains the project's responsibility.

# Review point

Review this decision when the service needs multiple nodes, the current region
or provider fails a recovery exercise, or another provider passes the complete
acceptance test with materially better cost or reliability. Record any provider
change in a new ADR after collecting that evidence.
