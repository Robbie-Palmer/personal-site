# Vision

Give each person a private development computer that remains available from a
phone or laptop. Coding agents continue working when the client disconnects,
and the person can return to the same files, processes, and context.

The workspace belongs to a person. It can hold related first-party
repositories, third-party code checked out for inspection or forking,
worktrees, local services, and multiple agent harnesses. T3 Code is the first
interface for directing Codex, Claude Code, OpenCode, Grok, terminals, browser
tools, and requests that need human attention.

# Problem

Local development ties active work to one device. Hosted task runners solve a
narrower problem: they execute a job in a fresh environment and return a
result. This project needs a durable working home where a person can move
between devices, supervise multiple agents, and leave long-running work in
progress.

Running that home on a remote server creates its own burden. Someone must
provision the machine, keep it patched, isolate users, preserve data, manage
access, and recover from failure. A useful service must make those jobs
repeatable enough for coding agents to inspect and help operate.

# Target user

The first users are developers who already direct coding agents for daily
work and want the environment available throughout the week. They are
comfortable bringing their own GitHub and model-provider accounts. They value
persistent multi-repository state and unattended execution enough to prefer a
hosted service over maintaining a server themselves.

The initial cohort is small and trusted. The product does not yet claim a
security boundary suitable for mutually hostile tenants or regulated
production data.

# Product requirements

Each user receives:

* a private, durable home directory and one or more working directories;
* access to T3 Code and the supported coding harnesses from a phone or laptop;
* work that continues through client disconnects;
* their own source-control and model-provider identities;
* resource limits that prevent an accidental workload from exhausting the
  shared host;
* encrypted backups with a tested restore path;
* a documented way to export their files and leave the service; and
* an operator who can provision, update, recover, and remove the workspace from
  versioned definitions.

Users must not share a home directory, provider login, private endpoint, or
ordinary service traffic. The workspace must not receive the host filesystem,
container-runtime socket, or cluster administrator credentials.

# Pilot

The project starts with two workspaces on one host. My workspace is the first
deployment. My brother's workspace is the first test of onboarding, identity,
isolation, recovery, and removal for another person.

The brother pilot is free while it fits inside spare capacity. It uses his own
GitHub and model-provider accounts. Success requires his workspace to survive a
restart and a host-replacement exercise, while my files and access remain
unaffected.

The pilot can use a trusted-user container boundary. Any move beyond a small
trusted cohort requires a separate isolation decision based on virtual machines
or microVMs.

# Current milestone

The repository now defines the operator and first pilot as separate K3s
workspaces. The operator keeps the existing namespace, volume, and private URL.
The pilot has a separate namespace, persistent-volume binding, Doppler config,
and tailnet port. Policy on the pilot blocks cross-workspace traffic. The
operator keeps its existing network behavior and its 3 CPU and 6 GiB limits.
The pilot starts with a 1 CPU and 1 GiB limit. That caps its additional pressure
without changing the operator's declared capacity, though both still share one
4 CPU, 8 GiB host and can contend for it. The pilot also runs at a lower,
non-preempting pod priority, making it the earlier eviction candidate when both
workspaces exceed their requests during node pressure.

The repository now declares a 10 GiB and 1,000,000-inode ext4 project quota for
the pilot without capping the operator workspace. The existing live volume
still needs the documented one-time filesystem maintenance before that quota
can take effect. Live onboarding then needs the pilot's Tailscale identity and
provider logins, followed by the concurrent-build, restart, access-revocation,
and file-isolation checks. Encrypted backup and replacement-host restore also
remain open before the pilot can meet the full success test.

Rendered workspace definitions now pass Flux Schema validation against pinned
Kubernetes 1.37 and Doppler Operator schemas. The check rejects missing schemas
and evaluates the Doppler custom resource's CEL admission rule before a live
cluster dry run.

# Success measures

The pilot succeeds when:

1. a new user can reach a ready workspace without manual changes to the host;
2. both users can run real coding work concurrently within their resource
   limits;
3. either workspace can restart without losing its home directory;
4. an encrypted backup restores onto a replacement host;
5. one user's access can be revoked and their workspace exported or deleted
   without disturbing the other user;
6. normal operation leaves no undocumented provider-console or host changes;
   and
7. operator interventions and peak resource use are recorded well enough to
   price a later invited cohort.

# Scope boundaries

The pilot does not include hostile-tenant isolation, an SLA, metered model
usage, automatic billing, per-user infrastructure spend caps, or a general
credential broker. Users continue to buy their own model access.

The project may later connect to the Work Graph and other knowledge services.
A repository and ordinary provider accounts must remain sufficient to use the
workspace.

# Open questions

* How many concurrent agents fit on the first host before memory, CPU, or disk
  contention affects another user?
* Does a workspace control plane remove enough onboarding and lifecycle work to
  justify operating it?
* Which files and sessions belong in an export, and which credentials must be
  revoked or excluded?
* How much operator time remains after onboarding and recovery are automated?
* Will invited users pay for continuity and maintenance when self-hosting stays
  available?
