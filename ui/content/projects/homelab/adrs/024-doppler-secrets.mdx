# Context

The homelab currently keeps credentials in gitignored local files and native
application stores. That avoids committing secrets, but it does not give a new
operator machine a common recovery path. The Ansible bridge and the planned
K3s cluster both need a secret source before they can perform unattended work.

Doppler already holds secrets for the other projects in this repository. A
separate homelab project avoids granting Ansible or K3s access to unrelated
Personal Site production secrets.

# Decision

Use the Doppler project `homelab` as the source of truth for homelab secrets.
The live environment uses its `prd` config.

Human-run mise commands authenticate through the local Doppler CLI. A command
that needs secrets will use `doppler run --project homelab --config prd` and
allowlist the names it needs. Ansible reads those values from the controller
environment, marks every consuming task `no_log: true`, and never copies a
complete Doppler config to a managed host.

Unattended workloads must not use a personal or CLI token. Give each one a
read-only Doppler service token scoped to a single config. Doppler documents
that boundary in its
[service-token guidance](https://docs.doppler.com/docs/service-tokens).

When the K3s pilot needs its first secret, install the
[Doppler Kubernetes Operator](https://docs.doppler.com/docs/doppler-k8s-operator-syncing-secrets).
Bootstrap its token through a local mise command that does not print the token,
then use namespace-scoped `DopplerSecret` resources. Do not give workloads the
Doppler token itself. Rotate or revoke a service token from Doppler and keep
the Kubernetes bootstrap procedure in the recovery runbook.

Treat the Ente CLI database at `~/.ente/ente-cli.db` as an exception. Ente uses
this native authenticated session database instead of a key-value application
secret. Keep it local with mode `0600`; do not encode or upload the database
to Doppler. Recreate it through Ente's interactive login on a replacement Mac.

Run this non-secret check to confirm that the operator can reach the correct
Doppler config:

```bash
mise run //homelab:doppler-check
```

# Recovery

A new human operator machine installs the Doppler CLI, signs in to the Doppler
workplace, checks out this repository, and runs the mise command above. Store
Doppler account recovery codes outside the homelab and repository. Existing
Kubernetes Secrets keep workloads running during a Doppler outage, but secret
rotation and a fresh cluster bootstrap wait for Doppler to recover.

# Alternatives

## Ansible Vault

Vault would encrypt repository values but still needs an out-of-band password
or key on every new operator machine. It also gives K3s no native rotation
path. Rejected because Doppler already solves access and recovery.

## SOPS with age

SOPS would keep encrypted files beside the manifests and works without a
hosted secret service. It still requires a separate age-key recovery design.
Reconsider it if dependence on Doppler becomes unacceptable.

## Keep gitignored files only

Local files work for the current single Mac but leave restoration and rotation
manual. Keep them during migration, then remove each one only after testing its
Doppler consumer and rollback path.

# Consequences

The repository can name secret contracts without containing their values.
Human access stays tied to Doppler identity. A scoped token limits unattended
access to one config. Doppler becomes a dependency for rotation and fresh
bootstrap, so test account recovery and token rotation before K3s becomes
unattended.
