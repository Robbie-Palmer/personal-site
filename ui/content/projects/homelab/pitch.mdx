# My phone reaches the same development machine as my laptop

t3-code runs on an always-on Mac mini behind Tailscale.

<PitchNotes>
  The Mac mini does the development work. The phone drives it. Repositories, tools, credentials, worktrees, browsers,
  and telemetry stay on the Mac mini.

  \[Sources]

  * [t3-code ADR](/projects/homelab/adrs/006-t3-code)
  * [Tailscale ADR](/projects/homelab/adrs/000-tailscale)
    \[/Sources]
</PitchNotes>

***

<h2 className="pitch-slide__long-title">Claude and Codex proved the phone workflow. t3-code removed the provider split.</h2>

I used Claude Code on the web from November and Codex cloud from April. Both made agent work from a phone normal.

Changing provider also changed the interface, session model, limits, and development environment. I wanted one
place to move between the Claude Code, Codex, Grok Build, and OpenCode harnesses without preparing the repo again.

<PitchStep>
  t3-code replaced the provider-specific remote interfaces. The harnesses and model subscriptions still do the work.
</PitchStep>

<PitchNotes>
  The comparison comes from my own use. Claude Code on the web and Codex cloud both support remote, persistent work.
  Their cloud sessions run in configured provider environments.

  \[Sources]

  * [Use Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)
  * [Codex cloud](https://learn.chatgpt.com/docs/cloud)
  * [t3-code ADR](/projects/homelab/adrs/006-t3-code)
    \[/Sources]
</PitchNotes>

<h2 className="pitch-slide__long-title">t3-code manages threads better, even before I change harness</h2>

<PitchColumns>
  <PitchColumn>
    ### Provider views

    * **Codespaces** gives me a hosted development machine with no home host.
    * **Claude and Codex cloud** keep work in their own task views.
    * **Claude Remote Control** exposes local Claude sessions, tools, and worktrees.
  </PitchColumn>

  <PitchColumn>
    ### t3-code

    * The sidebar shows running threads, work waiting for input, and old sessions to settle.
    * Diff, commit, push, and PR actions stay with the thread.
    * Four harnesses, each with many models and threads, share the same view. It still helps when I use only one.
  </PitchColumn>
</PitchColumns>

<PitchNotes>
  Codespaces remains useful when a disposable hosted machine is the goal. Claude and Codex cloud remain useful for
  background work that should not consume the Mac mini. Claude Remote Control gets closest to the local-machine part
  of this setup. t3-code puts thread state and GitHub actions in the same view. Harness switching adds to that.

## The feedback loop ends at the running service

<PitchColumns>
  <PitchColumn>
    ### An agent can use

    * the real repository and toolchain
    * isolated Git worktrees
    * authenticated GitHub commands
    * the browser used for debugging
    * live logs and telemetry
  </PitchColumn>

  <PitchColumn>
    ### It can check

    * the protected preview
    * a restart or reboot
    * a real health endpoint
    * the diff and pull request
    * physical Android and iOS later
  </PitchColumn>
</PitchColumns>

<PitchNotes>
  A typecheck is useful, but it does not prove that launchd restarted a service, a VPN gate held, or a page works on an
  old mobile browser. The proposed phone lab would give agents three real devices and repeatable screenshot tasks.

## Every solved problem leaves something the next one can reuse

1. Tailscale made the Mac mini reachable without a public service.
2. t3-code reused that host for four harnesses and their threads.
3. mise tasks, worktrees, a browser, and telemetry made changes easier to test.
4. The proposed phone lab can reuse the access, tasks, previews, and artifact collection.

<PitchStep>
  New work starts with access, commands, and feedback already working.
</PitchStep>

<PitchNotes>
  This is what cumulative value delivery means in this project. Each change solves its immediate problem and leaves a
  specific piece of infrastructure behind for later work.

## Old hardware gets jobs that suit the hardware

<PitchColumns>
  <PitchColumn>
    * The **Mac mini** runs agent sessions and services, and holds the 10TB disk.
    * The **Raspberry Pi** runs a second DNS server and connects to the printer over USB.
  </PitchColumn>

  <PitchColumn>
    * The **NixOS desktop** turns a GTX 1050 and 1TB disk into a GPU worker and DVC cache.
    * Three **retired phones** could become browser targets and a cellular watchdog.
  </PitchColumn>
</PitchColumns>

<PitchStep>
  A NAS is easier. Reusing the Mac and printer avoids two purchases.
</PitchStep>

<PitchNotes>
  Placement follows physical constraints. Disks stay with the Mac mini, the printer stays with the Pi, the GPU job
  stays with the machine that has a GPU, and phones are used for the browsers and radios servers cannot represent.

<h2 className="pitch-slide__long-title">Ente syncs photos. The lab owns the files and development workspace.</h2>

<PitchColumns>
  <PitchColumn>
    ### Complements

    * Ente remains the encrypted cloud photo service. An incremental export adds plain files on the 10TB disk.
    * Trakt remains the discovery and history layer. Jellyfin gives the owned library one place to play.
    * AI subscriptions still provide the models. t3-code provides the shared workspace.
  </PitchColumn>

  <PitchColumn>
    ### Replaces or postpones

    * t3-code replaces Claude and Codex remote interfaces in my daily workflow.
    * CUPS and Gutenprint postpone replacing a working 2011 Canon printer.
    * Ordinary disks and files avoid a NAS purchase and appliance lock-in.
    * A larger local library may make some streaming subscriptions unnecessary.
  </PitchColumn>
</PitchColumns>

<PitchNotes>
  The streaming claim is deliberately tentative. Netflix, Disney Plus, Amazon Prime, and Apple TV remain subscribed
  today. The current gain is a quicker route from Trakt discovery to Jellyfin playback for content already owned. A
  Synology NAS would package storage, backup, sync, clients, and administration more neatly. The current lab accepts
  more assembly work because the Mac mini and disk already cover the immediate jobs.

  \[Sources]

  * [Ente export documentation](https://ente.com/help/photos/features/backup-and-sync/export)
  * [Ente photo backup ADR](/projects/homelab/adrs/007-ente-photo-backup)
  * [Jellyfin ADR](/projects/homelab/adrs/011-jellyfin)
  * [CUPS ADR](/projects/homelab/adrs/012-cups)

<h2 className="pitch-slide__long-title">This is a personal setup, and the awkward parts are real</h2>

<PitchColumns>
  <PitchColumn>
    ### Failure modes

    * If the Mac mini is down, remote agent work stops.
    * Agent credentials and personal data share a host. Agents must not reach the photo disk.
    * The 10TB copy is in the same house. It does not cover theft or fire.
  </PitchColumn>

  <PitchColumn>
    ### Claims I cannot make yet

    * The phone lab remains proposed.
    * The media library cannot justify cancelling subscriptions yet.
    * I have not measured a cash saving. Agent-assisted maintenance has stayed roughly flat.
  </PitchColumn>
</PitchColumns>

<PitchNotes>
  I have not tracked maintenance time. Agents write configuration, run the same mise tasks I run, and repair routine
  failures. I still own the host, the permissions, and the consequences of a bad change.

# Reuse the pattern on hardware you already own

Use hardware you already own. Add private remote access, one agent interface, repeatable commands, and checks against
the running system.

<PitchStep>
  Fork the repo. Keep the decisions that solve a problem you actually have. Delete the rest.
</PitchStep>

<PitchNotes>
  I do not expect this to become a product. The useful output is a worked example that another engineer can inspect,
  challenge, and adapt.
